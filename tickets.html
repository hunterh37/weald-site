Tickets and agents

Weald's task system is a set of plain files inside your repository, and its agent interface is a local MCP server that reads and writes those same files. Both people and agents work against one record.

On-disk layout

Each project holds a visible, git-tracked .weald/ directory.

.weald/
  project.json          project identity and links to documents
  tickets/              accepted tickets
    WEALD-001.wealdticket
  proposals/            model-staged drafts, not committed
  events.log            append-only activity feed
  dismissed.json        remembered dismissals

Everything is committed except proposals/, which is ignored by git because a proposal is speculation and must not enter shared history before a person accepts it.

The ticket format

A .wealdticket file is Markdown with a YAML header. The format was chosen so that a ticket reads well in a text editor, produces a clean diff, and requires no tooling for an agent to parse. The custom extension exists so that macOS can associate an icon and file type with it.

---
id: WEALD-001
title: Add model fetching from OpenRouter
status: in_progress        # backlog | todo | in_progress | review | done | blocked
assignee: claude
priority: P2               # P0 | P1 | P2 | P3
created: 2026-07-21T10:00:00Z
updated: 2026-07-21T14:30:00Z
origin: agent              # human | agent | weald-llm
depends_on: [WEALD-000]
labels: [networking, mvp]
---

## Context
Why this ticket exists.

## Acceptance criteria
- [ ] Fetches the model list
- [ ] Caches locally with refresh

## Activity
- 14:30 claude: implemented fetch and caching

The origin field records provenance, distinguishing a ticket written by a person, one written by an agent performing sanctioned work, and one accepted from a model proposal. The interface always shows which it was.

A ticket may additionally be marked as a keystone, which designates it as a north-star item for the project and steers what Weald suggests next.

Concurrent writes

Several agents may hold the same ticket at once. Every write is performed as a temporary file followed by a rename, so a reader never observes a half-written ticket, and a writer checks the updated timestamp before overwriting in order to detect a clobber. Because tickets are tracked by git, history remains the final backstop.

Activity is recorded in events.log as one JSON object per line, which makes the file cheap to append to and to tail, and means it never has to be rewritten.

The MCP server

Weald is the MCP server and the agent is the client. The endpoint is http://127.0.0.1:47921/mcp over streamable HTTP, bound to the loopback interface only. There is no authentication token because the socket is not reachable from outside the machine.

ToolPurpose
weald_list_ticketsList tickets, optionally filtered by status
weald_get_ticketReturn one ticket in full
weald_create_ticketCreate a ticket
weald_update_statusChange status and append an activity note
weald_log_eventAppend an entry to the timeline
weald_set_statusDeclare the agent's current state and progress
weald_clear_statusClear the agent's rows
weald_askRaise a question that requires a person
weald_resolve_askMark a raised question as resolved
weald_notifySend a notification

When the application is running, tool calls change its state directly and the interface updates at once. When it is not running, the same changes land as file writes and are replayed at next launch. Agents therefore never depend on Weald being open; the file layer is the contract and the live connection is only an optimization.

Registering an agent

claude   mcp add --transport http weald http://127.0.0.1:47921/mcp
openclaw mcp add weald --transport streamable-http --url http://127.0.0.1:47921/mcp
hermes   mcp add weald --url http://127.0.0.1:47921/mcp

Claude Code stores the entry in ~/.claude.json and lists it with claude mcp list. Some gateways cache tool schemas and must be restarted after registration. Hermes exposes the tools under an mcp_weald_ prefix, with hyphens and dots converted to underscores, which is worth knowing if an agent reports that a tool cannot be found.

Agent status and the attention queue

Status declared by an agent is kept separately from status inferred from transcripts, and declared status is shown above inferred status. Each entry is keyed by agent and project, so two agents on one repository occupy two rows and one agent across repositories occupies a row per repository. Entries carry a state, a message, optional progress, and an expiry, so an agent that crashes mid-task expires rather than remaining pinned as working.

Everything awaiting a person is merged into a single ranked queue drawn from three sources: blocked and in-review tickets in the repository, GitHub items retrieved through the gh CLI, and questions raised by agents. Ranking places a stopped agent first, because it is the only item in the queue consuming time while it waits, then requested changes and review requests, then blocked tickets and assigned work. Within one kind, the item that has waited longest rises. The top of the same queue appears in the menu-bar panel.

Language-model features

Language-model features are optional and require an OpenRouter key, which is stored in the system Keychain and nowhere else. Where the local system supports on-device inference, that engine is preferred and no request leaves the machine at all.

The model is given exactly two jobs. It summarizes, producing a short account of what moved, what has stalled, and what is waiting on a person. Because a summary is read-only, it needs no approval, and it is cached rather than regenerated on every file change.

It also proposes. A proposal is written to .weald/proposals/, rendered as a visually distinct draft, and never becomes a real ticket until accepted. Each draft is editable in place, carries a line stating what it was generated from, and can be accepted, edited, or dismissed. Existing open tickets are supplied to the model with an instruction not to duplicate them, and dismissals are remembered so that the same suggestion does not return.

Generation is triggered deliberately: by a button, or quietly staged behind a badge after a session ends. Nothing is written to disk without a click either way.

Team and history

Weald answers who is working on what, and what is stuck, from version control alone, so the view is useful in a repository with no remote at all. It reads commit history with authorship and per-commit churn, branch tips, and how far each branch has diverged from the default branch. Where the gh CLI is available, pull requests and contributor identities are added on top. Results are published in stages as they arrive rather than after a single blocking call, so the view fills in progressively.
